## 0. 结论摘要

**最高优先级（会导致数据丢失 / run 卡死 / 跑错分支）：**

1. 编辑器保存时把「只有一条出边」的节点降级成 `next`，`when` / `condition` / 卡点 `outlet` 被静默丢弃。**打开一张单分支图、什么都不改、点保存就会丢。**
2. 两层及以上的内嵌子图里，`subagent.flowRef` 没有被递归收进快照；跑到该分支时派发失败、run 被判失败。
3. 运行图里点父 run 的「子运行」卡片选不中 child run（会话过滤把 child 排除在列表外），文档承诺的「点进 child 快照」不可用。
4. 属性面板清空 `when` 后保存不生效（UI 传 `undefined`，`buildFlow` 把旧 `when` 复活）——用户无法删掉确定性条件。
5. 图 id 未做路径校验：`aiworkflow_flow create` 可把 `flows/*.json` 镜像写到 `~/.aiworkflow/flows` 之外（路径穿越）。
6. `dispatched` 轨迹行被当成"执行了一次"：fan-out 节点在回路里的 `iterationLimit` / `maxRounds` 配额被翻倍消耗（6 轮上限实际只跑 4 轮）。
7. 自环节点的 `iterationLimit` 差一：配 2 次会执行 3 次，并且逃生轨迹谎称"未执行"。
8. `maxSteps`（run 级防绕圈）在 subagent 自动汇聚 / 路由路径上完全不生效：派发步回环可以无限跑。
9. 入口就是 `subagent` 且派发失败时，`start_run` 只返回自愈错误、不终结 run；run 一直停在 `running`（每次重试都同样失败）。
10. 派发步的崩溃窗口自愈会把刚补建的 child 立刻判成"未回报"再重派，留下一条无意义的失败 child。
11. 在子图层编辑「角色表」会被静默丢弃（保存成功、改动消失）。
12. 同一会话可以同时存在多个活跃 run，而 `complete_step` 只按 `hostSession` 解析到**最新**那个；旧 run 静默失联（已加"一会话一活跃 run"守卫 + 面板「放弃」入口，见 §11）。

**未完善（设计承诺了、代码没做）：** run 列表按 `cwd` 分组/分栏、运行图耗时/脉动/树形并排、`when` 分支不下发、多 child payload 结构、无取消/放弃 run 的入口等（§5）；`stale` 的三处文档说法互相矛盾（§5.4 / §6.1）。

**文档不同步：** 正式设计文档 §7.7 与 §9.2 自相矛盾；§9.1/§9.2 的编辑器与监控描述落后于实现；README / AGENTS / dsh-plugin README 多处与代码相反；`docs/dev` 三份"已实施"文档按约定应删除（§6）。

**发布：** 市场索引 `dsh-plugin/market/index.json` 仍钉在 `90d4c99`，落后 HEAD 12 个提交（其中 10 个改过插件产物）；从市场安装会装到 10-28 的旧版（§7）。

## 3. 高危缺陷（调用链 + 复现 + 修复）

### B1　单出边把 branches 降级成 next（编辑器数据丢失）

**位置**：`dsh-plugin/src/editor/model.ts:506-527`，关键在 `524-526`。

**调用链**：

```
保存按钮 / Ctrl+S
→ page.tsx:1087 save()
→ page.tsx:1091 composeRoot()
→ page.tsx:396 buildFlow(base, bodies, nodes, edges)
→ model.ts:502 outs = 该节点的出边
→ model.ts:506 outs.length === 1
→ model.ts:509 卡点且 outlet 已绑定？否
→ model.ts:524-526 node.next = single.target; delete node.branches
```

`canvasOf()`（`model.ts:418-428`）会把每个 branch 渲染成一条边，并带上
`data.branchId / condition / when`；但保存时只要该节点只剩一条出边，就会走"单边 = next"的
快捷路径，`branchId/condition/when/outlet` 全部没有落点。

**触发（三种，均已脚本证实）**：

1. 工具或历史数据写入 `n1.branches = [{ id:'b1', condition:'甲', when:"{{n1.payload.v}} == '1'", to:'n2' }]`
   （单分支是合法图，校验只给 `W_NO_DEFAULT` 警告）→ 在编辑器打开 → 不做任何修改 → 保存。
2. 编辑器内：`n1 → n2`、`n1 → n3` 两条边，给第一路填 `when`，删除 `n1 → n3` 那条边 → 保存。
3. 卡点：`branches: [{ id:'o1', condition:'继续', to:'n2' }]`（无 `outlet`，校验器按 `b.id === opt.id`
   认定已连线）→ 打开 → 保存。

**实际 vs 期望**：

- 情形 1/2：期望保留 `branches`，实际落库 `{"next":"n2"}`；`when`（服务端确定性路由）彻底消失，
  且保存前的实时校验用的是同一个 `composeRoot()`，页头仍显示「✓ 校验通过」。
- 情形 3：期望保留 `branches`（人工选未连线的 o2 应判失败），实际变 `next`；`answerGate` 在
  `branches.length === 0 && node.next` 时会放行**任何**选项（`engine.ts:644-646`），语义被改。

**证据**（审计用例 BUG-18 三组）：

```
单分支 when 往返：branches 消失 → next:'n2'
两分支删一条：     next:'n2'，when 丢失
卡点单条无 outlet：next:'n2'，branches 消失
```

**修复方案（补丁已实现）**：在单出边分支里判断这条边"本来是不是分支"
（`body.branches.length > 0` 或边上有 `branchId/condition/when`），是则仍写 `branches`，
保留 `when/outlet/condition`；只有全新、从未作为分支的单边才写 `next`。
已有的「卡点单边 + 显式 outlet」分支保持不变（`tests/editor-canvas.test.ts:85-109` 仍绿）。

### B3　会话过滤下 child run 选不中（运行图子运行卡片失效）

**位置**：`shared/src/sql.ts:201-223`（选择逻辑）、`shared/src/engine.ts:1253-1257`（child 不写 `host_session`）。

**调用链**：

```
运行图浮层/页签（runview/overlay.tsx:58 / page.tsx:69）
→ RunGraphPage 点「子运行」卡片：page.tsx:291 setSelected(child.id)
→ effect fetch `aiworkflow/?session=<sid>&run=<childId>`（page.tsx:85-87）
→ host.buildState（host.ts:73）→ readMonitorState(db, childId, {}, 'dsh:<sid>')

→ child run 的 host_session 是 NULL（insertChildRuns 的列清单里没有它，engine.ts:1255-1257）
→ sql.ts:215 `all.find(r => r.id === selectedId)` 落空
→ 回退 rootActive[0] / rootRecent[0]（= 父 run）
→ 返回 selectedId=父 run、detail=父 run
```

**实际 vs 期望**：期望切换 child 的图/轨迹并出现「← 父 run」；实际画面完全不变，child 卡片
`data-sel` 永远 false，也没有提示。不带 `session` 时同一请求能正确解析 child（说明只是过滤
条件把 child 排除，不是 child 数据缺失）。

**证据**：审计用例 BUG-1：`readMonitorState(db, 'run_child', {}, 'dsh:s1')` 返回

**修复方案（补丁已实现）**：`readMonitorState` 对"显式选中的 run"不再要求它出现在过滤后的

就允许选中。`active/recent` 仍只列本会话的根 run（面板列表不混入 child）。

> 注：不要改成"给 child 也写 host_session"——`latestRunByHostSession` 会把最新 child 当成主
> Agent 的 run，`complete_step` 会串到 child 上（见 B18 的同类问题）。

### B4　清空 when 后保存又复活

**位置**：`dsh-plugin/src/editor/page.tsx:907-916`（`setWhen`）、`editor/model.ts:541-542`（回退逻辑）。

**调用链**：

```
属性面板 when 输入框清空 → inspector.tsx:785 onChange('')
→ page.tsx:909 const when = value.trim() === '' ? undefined : value
→ edge.data.when = undefined
→ 保存 → buildFlow: const dataWhen = edge.data?.when;   // undefined
→ model.ts:542 when = dataWhen !== undefined ? ... : previous?.when
→ previous 是 body.branches 里的旧分支 → 旧 when 被写回
```

`undefined` 同时表示"这条边从没改过"和"用户清空了"，两者无法区分。

**证据**：审计用例 BUG-9：把 `edge.data.when` 显式置为 `undefined`（即现行 UI 行为）后，
`buildFlow` 产物仍带旧 `when`。

**修复方案（补丁已实现）**：UI 清空时显式写 `''`；`buildFlow` 对 `when === ''` 视为删除
（`dataWhen !== undefined` 分支里 `'' → undefined`）。`outlet` 同理：`onReconnect` 清空时写
`data.outlet = ''`，`buildFlow` 把 `''` 当"显式清除"，不再回退到 `previous.outlet`。

### B5　图 id 路径穿越（JSON 镜像写到数据目录之外）

**位置**：`shared/src/validate.ts:36`（只检查非空）、`shared/src/flows.ts:86-87`（直接拼路径写文件）。

**调用链**：

```
Agent 调 aiworkflow_flow action=create（tools.ts:161-179）
→ saveFlow(db, flow, flowsDir())（flows.ts:67）
→ validateFlow 只检查 `!flow.id`（validate.ts:36）
→ fs.mkdirSync(jsonDir)
→ fs.writeFileSync(path.join(jsonDir, `${stored.id}.json`), ...)（flows.ts:87）
```

`flow.id = '../escaped'` → `path.join(flowsDir, '../escaped.json')` 写到 `~/.aiworkflow/escaped.json`；
`../../...` 可继续外扩。`deleteFlow` 同样用 `path.join` + `fs.rmSync`，删除场景也可越界。

**证据**：审计用例 BUG-5：`validateFlow` 返回 `ok:true`，`saveFlow` 之后
`~/.aiworkflow/escaped.json` 存在（在临时 home 下验证）。

**修复方案（补丁已实现，双层防护）**：

1. `validateFlow` 拒绝含路径分隔符/Windows 非法字符/`.`/`..`/首尾空白的 id（允许中文与常规字符，
   避免破坏已有图）；

   不合法直接抛错（保存）或跳过镜像删除（删除）。

### B6　dispatched 轨迹占用迭代配额

**位置**：`shared/src/engine.ts:1231-1245`（写 dispatched）、`2047-2053`（execCount 统计所有行）、
`1869/1897`（上限判定）。

**调用链**：

```
fan-out subagent 在回路里
→ 每轮 gather / route 后 advanceTransaction 写一条 completed（iteration +1）
→ ensureChildrenSpawned → spawnChildren 又写一条 dispatched（engine.ts:1231-1245）
→ execCount(run, node) 统计 node_executions 的所有行（含 dispatched / limit_exceeded）
→ resolveAdvance 的上限判定用 execCount（engine.ts:1869, 1897）
```

**实际 vs 期望**：审计用例用 `iterationLimit=6` 的同一张图对比：

- 串行（无 fanOut）：node 完成 **6** 次（还多跑了 1 次，见 B7）；
- fan-out：只完成 **4** 次，然后逃生。

`maxRounds` 的控制器是 fan-out 节点时同样被翻倍消耗。

附带影响：面板「已走路径」把 dispatched 当成独立一步（×2、一直显示进行中，见 B16）。

**修复方案（补丁已实现）**：

- 新增 `executionCount()`：只统计 `completed/blocked`（真正执行过的），排除 `dispatched/limit_exceeded`；
- `resolveAdvance` 的上限判定改用它；
- 面板路径把 dispatched 与本轮 completed 合并（不增圈数）。

### B7　自环节点迭代上限差一

**位置**：`shared/src/engine.ts:430-442`（先算后继、后落完成行）、`1869-1913`（上限判定）。

**调用链**：

```
complete_step:
→ 取当前节点 node
→ 分支定位 successorId（可能是 node 自己）
→ resolveAdvance(run, snapshot, successorId)   // 完成行还没写
→ execCount(node) = 已落库的执行次数（N-1）
→ N-1 < iterationLimit  → 允许再次进入自己
→ advanceTransaction 才插入本次 completed（N）
```

对自环（`to` 指向自己）来说，判定总是少算当前这一次，结果是执行 N+1 次；最后一条
`limit_exceeded` 还写"未执行该节点"，与事实矛盾。

**证据**：审计用例 BUG-7：`iterationLimit=2` 的自环 prompt 实际产生 3 条 completed + 1 条 limit。

**修复方案（补丁已实现）**：`resolveAdvance` 增加 `pendingNodeId`（即将落库的完成节点）；
仅当**正要再次进入这个节点自己**时给计数 +1。回路里"进入另一个节点"的判定不加，
以保持既有语义（`tests/engine.test.ts:785-838` 的两条回路上限测试仍绿）。

### B9　入口派发失败，run 永远 running

**位置**：`shared/src/engine.ts:324-327`。

## 4. 中低危缺陷（编辑器 / 可用性）

### B16　面板「已走路径」把派发算两圈、一直显示进行中

`shared/src/progress.ts:64-87` 直接把 `node_executions` 按顺序合并。fan-out 节点一轮里有
`dispatched` + `completed` 两行：

- 路径条显示 `×2`（实际只走了一轮）；
- `statuses` 含 `dispatched` → `panel.tsx:259-263` 的 `stepTone` 返回 `running`（完成后仍在脉动）。

**证据**：审计用例 BUG-16：`count=2`、`statuses=['dispatched','completed']`。
**修复（补丁已实现）**：`buildPath` 把 dispatched 与紧随其后的 completed 合并成同一圈，
状态以 completed 为准；等待期只有 dispatched 时保留一条 `dispatched` 条目（面板仍能看到"停在这一步"）。

### B17　`when` 不命中时普通节点不自动走 default（文档冲突；已在 §11 按实现对齐文档）

- 设计 §7.3（`docs/...:294`）："有 when 都不命中、只剩 default → 自动走 default"；
- 代码：`completeStep` 调 `resolveBranch(..., allowDefault=false)`（`engine.ts:420`），
  只有 subagent 路由传 `true`（`engine.ts:934`）；
- 结果：普通节点不带 `branchId` 会收到自愈"需要选一条分支"（`engine.ts:1019-1025`），
  文案还说"没有 when 命中/默认分支"（其实有 default）。

同时 §7.3 表格第 5 行又说"branchId 缺失 → 不推进"，与第 4 行自相矛盾。
**需要产品决定**：是让普通节点也自动走 default（改 `allowDefault=true`），还是把文档改成
"必须显式选分支（含 default）"。审计不改代码，仅记录冲突；当前实现与第 5 行一致，且自愈可一次修好。

### B18　同会话多活跃 run 无互斥（设计缺口；已在 §11 加守卫与放弃入口）

- `startRun` 不检查 `hostSession` 是否已有活跃 run（`engine.ts:258-330`）；
- `latestRunByHostSession` 优先取**最新**活跃 run（`engine.ts:1769-1781`）；
- 工具层 `refOf` 不传 `runId`（`tools.ts:202`），只靠 hostSession；
- 结果：先起 A、再起 B 后，`complete_step` 推进的是 B，A 再也无法通过 hostSession 被推进（审计用例
  BUG-20 已复现：A `current_node=a1/steps=0`，B `steps=1`）。

设计 §8.1 只描述了单 run 的定位方式，没有定义多活跃 run 的语义；PENDING 也把"默认跟随哪个 run"
列为未决。**建议**：`start_run`/`POST /runs` 在会话已有活跃 run 时返回自愈错误（附当前 run 与
当前步），或显式支持 `runId` 入参；同时补一个"放弃 run"的入口（当前没有任何取消/放弃/标 stale 的
工具，僵尸 run 无法清理）。

### B19　子图层编辑角色表静默丢失

`page.tsx` 无条件把 `agents` 和 `onAgentsChange` 传给 Inspector（`1477-1501`），
「图 · 角色 N」页签在子图层也可编辑（`inspector.tsx:155-161`）；但：

- `composeRoot` 写回子图时只带 `{name, entry, maxSteps, nodes, _ui}`（`page.tsx:414-420`），
  `SubflowDef` 也没有 `agents` 字段（`types.ts:126-136`）；
- 父层 `buildFlow` 用的是 `frame.snapshot.agents`（`page.tsx:427`），即进入子图前的旧数组；
- `backToParent` 同样用 `frame.snapshot.agents`（`page.tsx:505`）；
- `loadGraph` 会用 `flow.agents ?? []` 覆盖 state（`page.tsx:378`）。

结果：改角色名/章程/新增角色 → 保存成功（banner「已保存」）→ 重新进入子图，改动全没了。

**修复（补丁已实现）**：角色表是全图共享的，折回父层时使用当前 state 的 `agents`
（`composeRoot` 的 `currentAgents`、`backToParent` 的 `snapshot.agents`），不再用 frame 快照里的
旧数组；撤销也能随之恢复。

### B20　reconnect 可把两条边挂到同一卡点出口

`page.tsx:776-813` 的 `onReconnect` 只重算 outlet，没有 `onConnect`（749-755）与
`completeOutletLink`（946-949）里的"出口已占用"检查。把一条普通边的起点拖到已占用的
`out-oN` handle 上，就会产生两条 `outlet` 相同的分支；`answerGate` 用
`branches.find(b => b.outlet === option.id)`（`engine.ts:639`）永远取第一条，第二条是死分支，
而画布显示两条都连通。当前校验器也不拦（补丁加了 `E_DUP_OUTLET` 兜底）。
**修复（补丁已实现）**：`onReconnect` 增加与 `onConnect` 对称的冲突检查。

### B21　卡点两个选项连同一目标被 UI 静默拒绝

`onConnect` 的去重是 `source + target`（`page.tsx:746`），没有考虑 outlet。卡点的两个选项都
指向同一个结束节点是合法图（DSL/校验/引擎都支持，审计脚本验证 `errors: []`），但画布上
第二次拖线会**静默 return**（连提示都没有）。**修复（补丁已实现）**：去重键加上 outlet；

### B22　设入口后的幽灵入边

`setEntryId` 只改 entry 与标记（`page.tsx:588-595`），不处理指向新入口的边；而入口节点不渲染
target handle（`canvas.tsx:57`）。React Flow 12 在找不到 target handle 时会 `onError('008')`

**修复（补丁已实现）**：设入口时在同一次 `record()` 里删除指向它的入边，并 `reportInfo` 告知。

### B23　dirty 误报 / 返回父层丢撤销（已在 §11 改为签名基线）

- `restore`（撤销/重做）末尾无条件 `setDirty(true)`（`page.tsx:366`），全文件只有保存成功那处
  `setDirty(false)`（`1098`）→ 撤销回保存时的状态仍显示"未保存"，离开会误弹确认；

`backToParent` 在写回前把父层旧快照压入 `frame.history.past`，写回无变化时不置脏。

### B24　Esc 一次收掉所有层（已修）

### B25　首路 condition 清空变 `*`、第二路却报错（已修）

## 7. 构建 / 发布脚本问题

（以下均在临时副本复现，未改动仓库；仓库当前产物与源码是同步的，见 §8.3。）

1. **`check:plugin` 部分暂存会假通过**：`check-bundles.mjs:16` 用**工作区源码**构建，

   手改过的产物会被静默覆盖。它本质是"重建式检查"，文档应说明。

   会构建并改写工作区，`:113-115` 跳过 commit（因此也不 `git add`）。要么改注释，要么 `--dry-run`
   只打印将执行的动作。

   全文件没有 reset/revert；失败时 `:40` 仍打印"什么都没提交"。建议改为按步骤报告并提示手动恢复。
5. **索引有效性只看两个产物**：`release.mjs:22` 的 `ARTIFACTS` 只有 `index.js/client.js`，
   `:85-93` 只比这两者。只改 `cordis.patch.yml` / `locale/*.json` / `icon.svg` / `package.json`

   建议把 `files` 清单里的所有文件都纳入比较。
6. **构建确定性依赖 `node_modules` 布局**：`client.js` 的 `//#region` 注释会带上依赖的物理路径。
